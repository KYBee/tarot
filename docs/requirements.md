# 기능 요구사항

관련 문서: [product-overview.md](./product-overview.md), [calculation-rules.md](./calculation-rules.md), [ui-ux-spec.md](./ui-ux-spec.md)

## 1. 기능 요구사항

### 1.1 입력

- 사용자는 생년월일을 입력할 수 있어야 한다.
- 초기 버전은 양력 기준만 지원한다.
- 회원가입, 로그인, 저장 기능은 포함하지 않는다.
- 입력 포맷은 `YYYY.MM.DD`를 기본으로 하되, 내부 파서는 `YYYYMMDD`, `YYYY-MM-DD`, `YYYY/MM/DD`도 허용 가능하다.

### 1.2 계산 결과

- 탄생카드를 계산해 보여줘야 한다.
- 페르소나 카드가 존재하면 별도 섹션으로 보여줘야 한다.
- 페르소나 카드가 없으면 빈 상태 문구를 제공해야 한다.
- 날개 카드를 계산해 보여줘야 한다.
- 작년/올해/내년의 연도 카드를 계산해 함께 보여줘야 한다.

### 1.3 결과 콘텐츠

- 각 카드 섹션은 카드 타입 설명, 기본 의미, 카드 설명, 프로필 설명 순서를 따라야 한다.
- 연도 카드 영역은 일반 카드 설명과 분리된 짧은 흐름 해석을 사용해야 한다.
- 결과 화면에 카카오 공유 버튼과 다시 하기 버튼이 있어야 한다.

### 1.4 공유

- UI에는 카카오 공유 버튼이 항상 존재해야 한다.
- 실제 Kakao SDK 키가 없을 때도 버튼은 비활성 또는 fallback 동작을 가져야 한다.
- 공유 문구는 탄생카드 중심으로 구성하되, 서비스명과 결과 링크를 포함할 수 있어야 한다.

## 2. 입력/출력 정의

### 2.1 입력값

- 필수 입력: 연도, 월, 일
- 입력 예시: `1997.10.17`

### 2.2 출력값

- 탄생카드 번호/이름/설명
- 페르소나 카드 번호/이름/설명 또는 단일 카드 타입 안내
- 날개 카드 번호/이름/설명
- 작년/올해/내년 연도 카드 이름과 흐름 해석

## 3. 계산 규칙

- 탄생카드: `YYYY + MM + DD` 이후 자리수 합산 반복, 최종 한 자리 숫자
- 페르소나 카드: 탄생카드 축약 과정에서 등장한 첫 번째 `10~22`
- 날개 카드: `탄생카드 - 1`, `1`의 이전 카드는 `0/22 바보`
- 연도 카드: `MM + DD + 대상 연도`, `22` 이하가 될 때까지 자리수 축약

계산의 상세 규칙은 [calculation-rules.md](./calculation-rules.md)를 따른다.

## 4. 예외 처리

- 잘못된 입력 포맷이면 즉시 오류 메시지를 보여준다.
- 존재하지 않는 날짜는 허용하지 않는다.
  예: `2026.02.30`, `2025.13.01`
- 윤년이 아닌 해의 `2월 29일`은 허용하지 않는다.
- 페르소나 카드가 없을 경우 "없음"이 아니라 서비스형 설명 문구를 사용한다.
- 카드 이미지가 없는 경우에도 텍스트 중심 결과 화면은 정상 동작해야 한다.
- 카카오 SDK가 로드되지 않거나 키가 없을 경우 공유 버튼은 fallback 동작을 사용해야 한다.

## 5. 비기능 요구사항

### 5.1 모바일 우선

- 기본 설계 기준은 360px~430px 너비 모바일 뷰포트다.
- 데스크톱에서도 읽기 가능해야 하지만, 카드형 모바일 경험을 우선한다.

### 5.2 반응형

- 결과 카드, 연도 흐름, 버튼 영역은 320px 이상에서 깨지지 않아야 한다.
- 데스크톱에서는 최대 폭을 제한해 카드형 몰입감을 유지한다.

### 5.3 접근성

- 입력 필드와 버튼에 명확한 레이블이 있어야 한다.
- 스와이프 카드와 도트 네비게이션은 스크린리더 문맥에서 이해 가능해야 한다.
- 텍스트와 배경의 명도 대비를 확보해야 한다.
- 모션은 과도하지 않아야 하며, 필요시 `prefers-reduced-motion`을 고려할 수 있어야 한다.

### 5.4 성능

- 첫 화면은 정적 리소스 기준으로 가볍게 로드되어야 한다.
- 계산은 클라이언트에서 즉시 처리 가능해야 한다.
- 콘텐츠 데이터가 커져도 UI 반응성이 떨어지지 않도록 데이터 접근 구조가 단순해야 한다.

### 5.5 유지보수성

- 현재 `index.html / script.js / style.css` 구조는 유지한다.
- 다만 카드 콘텐츠 데이터는 구현 단계에서 별도 JS 파일로 분리 가능한 구조여야 한다.
- 계산 로직, 렌더링 로직, 콘텐츠 데이터는 문서상 책임이 분리되어야 한다.
